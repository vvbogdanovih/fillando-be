# Обов’язковість характеристик категорій

`category-attribute-requiredness.js` додає **явний boolean `is_required` у кожну характеристику всіх категорій**. Для `filament.finish` та `filament.reinforcement` записує `false`, для решти — `true`. Включення у фільтри продовжує визначатися наявністю рядка в `required_attributes`, незалежно від прапорця. Значення характеристик товарів скрипт не змінює.

Відсутність прапорця після міграції — помилка. API та фронтенд вимагають boolean без default; генератор відмовляється замінювати XML, якщо бачить некоректний прапорець. Попередній XML зберігається в пам’яті поточного процесу; після перезапуску процесу та невдалої генерації публічний endpoint відповідає 503.

## Порядок релізу

1. Підготувати обидві збірки. Для нової бази відновити актуальний дамп. Старий ланцюжок каталогу видалено; якщо дамп ще не містить явних прапорців, виконати цю міграцію перед запуском нової версії. Якщо журнал уже має `complete`, скрипт перевірить дані без перезапису налаштувань.
2. На час міграції зупинити **всі** записи категорій (адмінку, імпорти, старі міграції, фонові завдання) та генерацію фіда. Старий бекенд при збереженні категорії викине новий прапорець; змішаний реліз неприпустимий. Прямий скрипт не викликає API інвалідації кешу.
3. У каталозі бекенду встановити `DATABASE_URL` потрібної бази через захищене середовище. За відсутності змінної використовується `.env`. Скрипт виводить назву бази, не URI. Перевірити ціль і dry-run:

    ```sh
    node scripts/migrations/category-attribute-requiredness.js --dry-run
    ```

4. Застосувати й перевірити:

    ```sh
    node scripts/migrations/category-attribute-requiredness.js --apply
    node scripts/migrations/category-attribute-requiredness.js --verify
    ```

5. Лише після успішного `--verify` запустити нові бекенд та фронтенд, очистити кеш категорій у всіх інстансах фронтенду (або виконати чинну інвалідацію `categories`). Відновити записи, перегенерувати фід. Перевірити CF/GF/Silk, лічильники, збереження `false` після редагування та відсутність саме цих двох попереджень.

## Що вважається повним успіхом

- Перевірено всі сирі документи `categories` через MongoDB driver, без Mongoose defaults.
- На першому запуску знайдено рівно одну категорію `filament` та обидва ключі. Некоректні масиви, порожні/повторні ключі, `null`, рядки чи конфліктні наявні прапорці зупиняють запуск **до записів категорій**.
- Dry-run не пише навіть журнал. `--apply` спершу зберігає повні документи до/після та SHA-256 контрольну суму в `catalog_migrations`, `_id = category-attribute-requiredness-v1`, і перечитує backup. Backup і кожен запис підтверджуються з `w: majority`. За плану понад 12 MiB скрипт відмовляється від запису — таку міграцію потрібно розбити.
- Кожне оновлення звіряє весь попередній документ атомарним фільтром. Змінюється лише `required_attributes`; порядок, поля характеристик, Google-категорія, timestamps та інші дані зберігаються.
- Після запису перечитуються **всі** категорії. Звіряються кількість, ідентичність і повний вміст документів із планом, а також кожен boolean. Лише тоді журнал отримує `complete`. Підсумок показує категорії, поля, `true`, `false`, `missing: 0`.
- Будь-який збій дає ненульовий exit code. Частковий запис не є успіхом.

## Збій, повторний запуск і відкат

Запускати лише один екземпляр скрипту. Перед `--resume` чи відкатом переконатися, що попередній процес зупинено; це явні операторські команди відновлення, не автоматичний паралельний запуск.

```sh
# Показати збережений план незавершеного запуску без записів
node scripts/migrations/category-attribute-requiredness.js --dry-run
# Продовжити той самий план; уже записані документи перевіряються й пропускаються
node scripts/migrations/category-attribute-requiredness.js --resume --apply
# Переглянути відкат, потім застосувати його
node scripts/migrations/category-attribute-requiredness.js --rollback
node scripts/migrations/category-attribute-requiredness.js --rollback --apply
```

Після збою залишити записи категорій і генерацію зупиненими. Якщо змінено інші поля/склад категорій, скрипт відмовиться перезаписувати їх і назве проблемний документ. Розібрати конфлікт перед продовженням. Відкат працює і після часткового запису, і після успіху; повертає точний стан із backup, включно з відсутністю нового поля. Незавершений відкат продовжується тією ж командою `--rollback --apply`.

Після відкату повернути сумісні попередні збірки перед відновленням роботи. Журнал не видаляти. Повторне впровадження після відкату оформлювати новою переглянутою версією міграції.

Повторний `--apply` після `complete` лише перевіряє повноту поточних даних; не скидає пізніші рішення адміністратора. Якщо прапорець зник після старого імпорту, перевірка падає — автоматичного маскування немає.

## Перевірка на тимчасовій MongoDB

```sh
REQUIREDNESS_TEST_URL=mongodb://127.0.0.1:27029/fillando_test_requiredness \
  node --test scripts/migrations/category-attribute-requiredness.integration.test.js
```

Тест приймає лише loopback URI із цим тестовим ім’ям і використовує окрему базу із суфіксом PID. Перевіряє всі категорії, відсутність змін товарів, dry-run, повторний запуск, пропуски, некоректні дані, збій запису, продовження, відкат, зовнішні правки та пошкодження backup.
